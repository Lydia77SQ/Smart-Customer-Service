# 竞品分析：智能客服系统（内部 IT / 行政支持）

## 调研背景

- 场景：公司内部 IT 与行政支持，不是面向外部客户的电商客服。
- 现状：员工人工找对接人；夜间无人、找不到人。
- 已锁定形态：Web + AI 先答、可转人工；员工端 / 坐席端 / 知识库 三页。
- 角色、工单何时创建、记录可见性：用户暂定。下文方案按「单组织、对话即工单、员工只看自己」作为默认假设，阶段 A 可改。

---

### 竞品一：飞书服务台（国内）

- 一句话定位：给企业内部员工用，在飞书里用 AI 问答 + 人工客服 + 工单，解决「不知道找谁、重复问同样的问题」。

**① 做了哪些功能**

- AI 问答机器人：欢迎语、常见问题卡片、知识库关联，拦截大量重复咨询（官方宣称可覆盖约 80% 常见问题）。
- 文档直连问答：不必先把制度拆成 FAQ，机器人直接消化文档再回答。
- 转人工 / 匹配专家：复杂问题按技能组或问题类型分给内部对接人；转接前可填询前表。
- 智能工单：会话中建单、改状态、打标签、流转；群聊记录可生成工单。
- 服务台可按部门拆（IT、行政、人事），员工选台或由总台分流。
- 数据报告：机器人准确率、人工效率、满意度。

**② 功能取舍的逻辑**

- 做深「找得到人 + 拦住重复问」：痛点就是员工不知道找谁、职能部门被重复问。夜间无人时靠机器人顶住。
- 做浅独立「坐席工作台」：客服在飞书会话里打开工单面板即可，不单独做一套 Inbox。
- 不做对外电商店铺客服、全渠道（微信/网页插件是附属），核心绑在飞书 IM。
- 知识权限跟飞书文档权限走，而不是单独再造一套上传切块流水线。

**③ 页面布局 / 视觉风格 / 配置方案**

- 页面布局：员工侧是聊天会话 + 顶部常见问题卡片；人工侧仍在会话里，右侧/面板打开工单信息、状态、标签。入口嵌在飞书，而不是独立四页系统。
- 视觉风格：飞书蓝白、卡片化、轻量办公风，少用重后台表格。
- 配置方案：管理员配欢迎语、问题分类卡片、知识库/文档关联、转人工规则、技能组、询前表、满意度。员工几乎不配。

### 竞品二：Jira Service Management（国际，内部 IT 标准形态）

- 一句话定位：给企业内部 IT / 服务台用，员工从门户提问或提单，虚拟代理先答，答不了再进坐席队列。

**① 做了哪些功能**

- 员工门户：按请求类型（账号、设备、权限、故障）进入，而不是只有一个自由聊天框。
- Virtual Service Agent：意图流程（逐步收集信息）+ AI Answers（检索关联知识库并总结回答，记住追问上下文）。
- 答不了或员工要求人工 → 创建工单（Issue），带上对话里已收集的信息。
- 坐席队列：列表 / 看板 / 日历；默认状态接近「待办 / 处理中 / 完成」；可按 SLA 排序。
- 知识库（常挂 Confluence）：员工自助搜文章；AI 从已链空间生成答案。
- 坐席辅助：分类、摘要、建议回复（偏 Copilot，不是员工端同一条生成链路）。
- 渠道：门户、邮件、Slack、Teams。还有服务目录、变更、资产等 ITSM 重能力。

**② 功能取舍的逻辑**

- 做深「工单生命周期与责任」：内部 IT 要的是谁在处理、卡在哪、何时完结，而不只是聊完即走。
- AI 分成两路：结构化意图流程（改密码、领电脑）走脚本；开放问答走知识库生成。模糊时先确认意图再开流程。
- 做浅「纯聊天客服」：员工侧更像门户 + 对话，不像独立客服 App；坐席侧是队列而不是即时 Inbox。
- 明显缺失：不把「上传 Markdown → 切块 → 向量/关键词双库」做成产品主路径；知识依赖 Confluence。不做电商导购、营销机器人。SLA、CMDB、变更管理对本项目过重。

**③ 页面布局 / 视觉风格 / 配置方案**

- 页面布局：员工端是帮助中心（分类入口 + 搜索/对话）；坐席端左侧队列、中间工单详情与评论、知识在侧栏或新标签。看板列对应状态。
- 视觉风格：Atlassian 蓝、白底、强表格/看板，偏生产力工具而非消费级聊天。
- 配置方案：项目管理员配请求类型、虚拟代理意图与 AI Answers 开关、知识空间、队列与状态。员工只提交请求。

### 竞品三：智齿客服（国内，对照「员工端 + 坐席 Inbox + 知识库」）

- 一句话定位：给企业客服团队用（偏对外客户，也有内部知识），机器人先答，转人工进坐席工作台，工单与知识库打通。

**① 做了哪些功能**

- 问答/大模型机器人：知识库自动回复、任务流程多轮收集信息、转人工规则（关键词、手动、技能组）。
- 机器人与人工分段：机器人处理期间人工不插话；转人工后机器人不再介入。
- 坐席 Inbox：左会话列表、中对话、右客户信息 / 知识库 / 快捷回复 / 工单。
- 智能回复：坐席输入时检索知识，可改后再发（辅助坐席，不是替坐席自动发出）。
- 工单中心：机器人可接待工单、转人工路由、分类与流转。
- 知识库：标准问匹配（智能/完全/包含）、内部知识仅坐席可见、未知问题学习。

**② 功能取舍的逻辑**

- 做深「接待效率」：列表+对话+右侧知识是专职坐席的标准桌面，减少切窗口。
- 机器人负责拦截，人工负责闭环；转人工是硬切换，避免人机抢话。
- 做浅企业内部「找对接人 / 夜间自助」叙事：产品基因是对外在线客服，不是 IT 服务台。
- 不做员工自己维护 Markdown 切块双路检索的研发向知识流水线；知识以问答条目为主。
- 全渠道、质检、统计对本项目过重。

**③ 页面布局 / 视觉风格 / 配置方案**

- 页面布局：控制台左侧模块（工单、用户、知识库、设置）；坐席工作台为经典三栏 Inbox。
- 视觉风格：SaaS 后台蓝灰、高信息密度、列表+详情。
- 配置方案：管理员配机器人、知识、转人工规则、技能组；坐席配在线状态、快捷回复。访客几乎无配置。

## 对比与取舍（对本项目）

| 维度 | 飞书服务台 | Jira Service Management | 智齿客服 | 本项目更适合学谁 |
| --- | --- | --- | --- | --- |
| 场景 | 内部 IT/行政/人事 | 内部 IT 服务台 | 偏对外客服 | 飞书 / JSM 的场景 |
| 夜间无人 | 机器人 24h 顶第一线 | 虚拟代理 24h | 机器人 24h | 三者都要学 |
| 员工入口 | 聊天 + FAQ 卡片 | 门户分类 + 对话 | 咨询窗 | 聊天为主（已画员工端） |
| 坐席桌面 | 嵌在 IM | 队列 + 工单详情 | 三栏 Inbox | 智齿式三栏，贴合已画坐席端 |
| 工单 | 有，偏轻 | 很重（队列/SLA/类型） | 有，与会话分段 | 轻量：处理中 / 已完结 |
| 知识 | 文档 + FAQ | Confluence | 问答条目 | 用户已定：仅 .md 入库 + QA/RAG |
| 转人工 | 匹配专家 | 建 Issue 进队列 | 硬切换结束机器人 | 员工主动转人工 + 坐席接入 |
| 不做 | 绑飞书生态 | SLA/CMDB/变更 | 全渠道/质检 | 本 MVP 都不做 |

用户已定、竞品里要保留的差异点：

- QA 库高相似度（≥ 0.8）直接返回答案，再走意图 / 记忆改写 / RRF 混合检索。
- 意图模糊则反问，不急着生成。
- 员工「检索生成」与坐席「智能回答」走同一条链路。
- 知识只收 Markdown，切块进向量 / 关键词 / 元数据（SQLite）。

## 可选方案

**方案 A：飞书服务台式（内部自助优先）**

- 员工端聊天 + 常见问题入口；夜间全靠 AI。
- 坐席侧偏轻，复杂问题再找人。
- 风险：坐席工作台偏弱，和已画的工单列表/分类/结单不完全对齐。

**方案 B：JSM 式（工单队列优先）**

- 员工先选 IT/行政类别再提问；坐席以队列和状态为主。
- 风险：门户分类过重；AI 与工单拆成两套系统，和「对话即服务」不一致。SLA/资产不纳入 MVP。

**方案 C：智齿式（Inbox 接待优先）**

- 三栏坐席台 + 机器人先答再转人工。
- 风险：产品叙事偏外部客服；缺「找不到内部对接人」的引导。

**方案 D（推荐）：融合**

- 场景与目标学飞书服务台：内部 IT/行政、AI 先拦重复问、夜间可问、转人工是为了找到人。
- 页面结构学智齿：登录 → 员工聊天 → 坐席三栏（工单列表 + 对话 + 分类/智能回答）→ 知识库上传。
- 工单状态学 JSM 的简化版：待接入/AI 接待、处理中、已完结；已完结不可再发（用户已定）。不引入 SLA、CMDB、服务目录。
- AI 链路用用户已定流程，不抄竞品的「纯 FAQ 匹配」或「只绑 Confluence」。
- 暂定项的默认假设（阶段 A 可改）：
  - 角色：MVP 同一账号可进三个页面（图上已有跳转）；不先做严格分权。
  - 工单：员工发问即产生会话/工单；点转人工后进入坐席待处理；坐席点处理中再回复。
  - 记录：对话全部保存；员工只看自己的；坐席看待处理与处理中工单；MVP 不提供导出下载。
  - 知识库：登录用户可看、可上传 .md（与跳转入口一致）；不做多租户。
